# 店舗POS MVP Week 1 実装チケット

最終更新: 2026-05-12

このドキュメントは、店舗POS MVP の最初の1週間で着手する実装単位をまとめたものです。

対象前提:
- 既存モバイルオーダー基盤を再利用する
- まずは **POS注文を正しく作り、支払受領まで回せる骨格** を作る

---

## Ticket 1: POS用データモデルの追加案を作る

目的:
- 既存注文テーブルへ追加すべき項目を整理する

作業:
- `order_source`
- `payment_method`
- `payment_status`
- `paid_at`
- 必要なら `terminal_label`
の追加案を作る
- SQL たたき台を作成する

完了条件:
- DB変更案が明文化される
- 既存モバイルオーダーへの影響範囲が分かる

---

## Ticket 2: 型定義に POS 注文項目を追加する

目的:
- `store_pos` を扱う型の土台を作る

作業:
- `src/types/database.ts`
- 関連注文型
- payment method / status の union 型追加

完了条件:
- POS注文を型で表現できる

---

## Ticket 3: POS注文作成 API の設計を分離する

目的:
- 既存公開注文APIを流用しつつ、POS専用入口を用意する

作業:
- 既存モバイルオーダー作成APIの再利用ポイント整理
- `store_pos` 注文作成 API の追加
- 在庫減算を既存ロジックへ寄せる

完了条件:
- POS注文を API から作成できる
- 在庫が正しく減る

---

## Ticket 4: タブレット向け POS 注文画面のワイヤー実装

目的:
- 老若男女が操作しやすい店頭 UI の最小版を出す

作業:
- POS専用ページ追加
- 商品一覧
- カート
- 支払方法選択
- 注文確定
- 注文完了画面
  - `次の注文を始める` CTA
  - 自動で商品一覧へ戻る導線
  - 戻る時の状態リセット

完了条件:
- タブレット上で最低限の注文ができる
- 注文完了後に次のお客様へ自然に引き継げる

---

## Ticket 5: 支払受領フローの API を追加する

目的:
- 注文作成と支払確定を分離する

作業:
- `payment_status = pending` で注文作成
- `料金受領` で `paid` に更新する API

完了条件:
- 支払受領を明示的に確定できる

---

## Ticket 6: 注文管理ダッシュボードに POS 情報を出す

目的:
- 既存ダッシュボードで POS注文を扱えるようにする

作業:
- 注文ソース表示
- 支払方法表示
- 支払状態表示
- `料金受領` ボタン追加

完了条件:
- 店員が同じ画面で POS 注文を処理できる

---

## Ticket 7: ベンダー支払方法設定を追加する

目的:
- 現金 / PayPay / その他 をベンダーごとに管理できるようにする

作業:
- 設定画面追加
- API追加
- POS画面で反映

完了条件:
- ベンダー設定に応じて POS画面の支払方法が切り替わる

---

## Ticket 8: POS売上を分析へ合流させる

目的:
- 表示上の売上をモバイルオーダーと合算する

作業:
- 既存分析APIの集計対象へ POS 注文を追加
- `order_source` を裏側で保持

完了条件:
- 既存分析に POS 売上が乗る

---

## Week 1 の完了ライン

1週間目の完了ラインは以下です。

1. POS注文のデータモデルが固まる
2. POS注文を作成できる
3. POS注文でも在庫が減る
4. 支払受領をダッシュボードで確定できる
5. 注文管理画面で POS 注文を扱える

この時点では、
- レシート
- 本格的な会計運用
- 高度な分析切替

までは未着手で問題ありません。
