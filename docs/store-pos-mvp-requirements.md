# クリダス 店舗POS MVP 要件整理

最終更新: 2026-05-12

## 1. 目的

既存のモバイルオーダー基盤を活用しながら、店頭設置タブレットで注文受付できる **店舗POS MVP** を実装する。

このMVPの目的は以下です。

- 店頭注文をクリダス上に注文データとして蓄積する
- 現金 / PayPay を前提に、店員オペレーションを阻害しない会計フローを作る
- モバイルオーダー注文と同じ注文管理ダッシュボードで対応できるようにする
- POS売上も、モバイルオーダー売上と同様に分析へ活用できるようにする

---

## 2. MVPの前提

### 対象利用シーン

- キッチンカーの注文カウンター
- 小規模飲食店の店頭カウンター
- イベント出店時の簡易POS

### 利用端末

- iPad などのタブレットを店頭に設置
- お客様がタブレットを直接操作して注文
- 店員は横で声がけし、必要に応じて注文補助・会計受領を行う

### MVPで実現すること

- 店頭タブレットで商品選択・注文作成
- 会計方法の選択
- 店員による料金受領確定
- 注文管理ダッシュボードでの一元運用
- 既存分析への売上統合
- モバイルオーダー在庫との在庫連動

### MVPで後続に回すこと

- レシート発行
- 外部POS / 会計ソフト自動連携
- 複数会計担当・レジ締め
- 返品 / 返金処理の詳細設計
- 現金過不足管理
- 割引 / クーポン / ポイント
- 本格的なキャッシュドロワー連携

## 3. 基本方針

### 3-1. 注文入口

- **基盤は既存の公開注文ページを流用する**
- ただし、モバイル向け公開注文ページをそのまま使うのではなく、**タブレット据え置き前提の POS 専用UI** を新たに作る
- 再利用するのは以下
  - 商品一覧取得
  - オプション構成
  - カート計算
  - 注文作成API
  - 注文管理ダッシュボード

### 3-2. 支払方法

- お客様が注文確定前に支払方法を選ぶ
- MVP対象の支払方法
  - 現金
  - PayPay
  - その他
- 有効な支払方法は **ベンダー管理画面で設定可能** にする
- POS画面では、その設定に基づいて選択肢を表示する

### 3-3. 会計確定タイミング

- **注文作成時ではなく、支払受領時に会計確定** とする

推奨フロー:

1. お客様が商品と支払方法を選んで注文を作成する
2. 注文は `payment_status = pending` で保存される
3. 店員が注文管理ダッシュボード上で **料金受領** を押す
4. その時点で `payment_status = paid` になる

この方式を採用する理由:

- 現金 / PayPay の受領確認を店員が責任持って確定できる
- お客様が誤って注文だけ作って離脱した場合に、未払い注文として識別できる
- モバイルオーダーのオンライン決済済み注文と区別しやすい

代替案:

- タブレット側に「支払い完了」ボタンを置く案もある
- ただし MVP では、**店員側ダッシュボードで確定する方が安全** と判断する

### 3-4. 分析統合

- 表示上の売上・注文数は **モバイルオーダーとPOSを合算** する
- ただし DB上では、**注文ソースを必ず保持** する

最低限必要な区分:

- `mobile_order`
- `store_pos`

これにより、将来

- POS比率
- 店頭注文と事前注文の比較
- 支払方法別分析

を可能にする

### 3-5. 在庫連動

- POS注文でも、既存モバイルオーダーと **同じ在庫を減算** する
- つまり、モバイルオーダーと POS の在庫は別に持たず、同一の商品在庫を共有する

期待される挙動:

- POSで売れたらモバイルオーダー側の在庫も減る
- モバイルオーダーで売れたら POS 側の在庫も減る

## 4. ユーザー体験

### 4-1. お客様の体験

1. 店頭タブレットで注文画面を開く
2. 商品とオプションを選ぶ
3. 会計方法を選ぶ
4. 合計金額を確認する
5. 店員に現金または PayPay で支払う
6. 注文完了後、呼び出し用の番号または受付番号を確認する

### 4-2. 店員の体験

1. 注文管理ダッシュボードに新規注文が入る
2. `未払い` の注文として見える
3. 支払受領後に `料金受領` を押す
4. 必要に応じて `調理中` `完成` `受取済` を更新する

### 4-3. ベンダーの管理体験

1. POSで使う支払方法を設定する
2. タブレット用注文画面を開く / 固定表示する
3. モバイルオーダーとPOSの注文を同じダッシュボードで管理する
4. 分析では合算値を見つつ、必要ならソース別に切り分けられる土台を持つ

## 5. MVP画面一覧

### 5-1. ベンダー管理画面

- POS設定トップ
- 支払方法設定
- タブレット表示用 POS 注文画面起動導線
- 既存注文管理ダッシュボード（POS対応拡張）

### 5-2. タブレット注文画面

- 商品一覧
- 商品詳細 / オプション選択
- カート
- 支払方法選択
- 会計確認
- 注文完了

#### 注文完了画面で必要なこと

- 主CTAとして **`次の注文を始める`** を大きく配置する
- 補助的に、商品一覧へ戻る導線が分かる文言にする
- 一定時間操作がなければ、自動で商品一覧へ戻る
- 自動復帰時は、前のお客様の
  - カート
  - 支払方法選択状態
  - 入力済み情報
  を確実にリセットする
- 小さく `まもなく次の注文画面へ戻ります` のような案内を表示する

### 5-3. 既存注文管理ダッシュボードで追加するもの

- 注文ソース表示
  - モバイルオーダー
  - 店頭POS
- 支払方法表示
- 支払状態表示
- `料金受領` アクション

---

## 6. データモデル方針

既存モバイルオーダーの注文テーブル群をなるべく再利用し、以下を追加または拡張する。

### 必須追加項目

- `order_source`
  - `mobile_order`
  - `store_pos`
- `payment_method`
  - `cash`
  - `paypay`
  - `other`
- `payment_status`
  - `pending`
  - `paid`
- `paid_at`
- `pos_device_label` または `terminal_label`（任意）

### ベンダー設定で追加したい項目

- `enabled_payment_methods`
- `default_pos_mode_enabled`
- `pos_terminal_name`（任意）

---

## 7. 分析要件

### MVPで必要なこと

- 既存売上分析では **POS売上とモバイルオーダー売上を合算表示**
- 将来分析用に、裏側では `order_source` を保持

### MVP段階ではまだ不要なこと

- 画面上でソース別切替を必須にしない
- 支払方法別ダッシュボードを必須にしない

---

## 8. MVP完了条件

以下を満たしたら MVP 完了とする。

1. 店頭タブレットから商品を注文できる
2. 支払方法を選べる
3. 店員がダッシュボードで料金受領を確定できる
4. POS注文が既存注文管理ダッシュボードに表示される
5. POS注文でも在庫が減算される
6. 既存分析にPOS売上が合算される
7. 裏側では `mobile_order / store_pos` を区別できる
