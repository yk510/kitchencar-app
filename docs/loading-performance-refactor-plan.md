# ローディング体験 改善リファクタ計画

最終更新: 2026-05-15

## 目的

このリファクタの目的は、アプリ全体の

- 初回表示が遅い
- 画面遷移時に待たされる
- 注文系の操作後に「押せたか不安」になる
- 分析画面やダッシュボードで空白時間が長い

といった体感上のストレスを減らすこと。

特に今回は、**実測の絶対速度** だけでなく、**待っていることが分かる / すぐ触れる / 途中で止まって見えない** を改善対象にする。

---

## 現状の主なボトルネック

### 1. `cache: 'no-store'` と dynamic page が広い

以下のような画面・APIで `no-store` や動的描画が多く、毎回フル取得になっている。

- 認証まわり
- 注文ダッシュボード
- モバイルオーダー公開ページ
- POS 公開ページ
- 分析系 API / 画面

結果として、

- 画面を開くたびに待ちが出る
- 一部の画面で First Load が重い
- 復帰時にも同じ取得が走る

状態になりやすい。

### 2. 認証確立と profile summary 待ちがまだ広い

`AuthProvider` はかなり整理済みだが、まだ

- `getSession()`
- `refreshProfile()`
- `router.refresh()`

の組み合わせで、初回表示時に待ちを作りやすい。

### 3. ポーリング中心の画面が複数ある

以下はポーリングに依存している。

- 注文ダッシュボード
- 公開モバイルオーダー画面
- POS 画面
- organizer/vendor 一部画面

これ自体は悪くないが、**初回ロード・復帰・新着反映** が別々に実装されていて、無駄取得や待ちが発生しやすい。

### 4. 「読み込み中の見せ方」が画面ごとに不揃い

最近 `LoadingLine` を一部導入したが、

- まだ空白待ちの画面がある
- 遷移中と取得中が見分けにくい画面がある
- skeleton が不足している画面がある

ため、遅く感じやすい。

### 5. 分析画面は「データが重い + 表示が後勝ち」

分析画面は server 側でまとめて取得しているものが多く、

- 先に骨組みを出す
- 重い集計だけ後から描画する

の分離がまだ十分ではない。

---

## 改善方針

### 方針 1. 毎回最新が必要な場所だけ `no-store`

リアルタイム性が必要な画面:

- 注文ダッシュボード
- 公開注文ページ
- POS 画面

は動的優先でよい。

一方で、

- ベンダー設定画面
- 商品設定
- 原価登録
- 分析トップの一部サマリー

は、短い revalidate や client-side refresh へ寄せられる余地がある。

### 方針 2. 「先に描画」「あとで更新」を増やす

以下を徹底する。

- shell を先に出す
- 初回に不要な詳細は後で取得
- 集計は skeleton で待たせる

### 方針 3. ポーリングの共通化

注文 / POS / モバイルオーダーの監視系は、

- 初回ロード
- visibility 復帰
- focus 復帰
- interval

の扱いを共通 hook に寄せる。

### 方針 4. ローディング UI の統一

以下の3種類を用途別に使い分ける。

- `LoadingLine`: 操作後の遷移待ち
- skeleton: 表示領域の埋まり待ち
- banner/toast: バックグラウンド更新の通知

---

## 実装フェーズ

## フェーズ A

### テーマ

認証と注文系の待ち時間を減らす

### やること

1. `AuthProvider` の `refreshProfile()` 呼び出し条件をさらに絞る
2. `router.refresh()` を本当に必要な auth event に限定する
3. 注文ダッシュボード / 公開注文 / POS のポーリング共通 hook を作る
4. 注文画面で `LoadingLine` を使っていない操作を洗い出して統一する

### 完了条件

- ログイン直後の待ちが減る
- 注文ダッシュボード復帰時の待ちとブレが減る
- 注文画面の操作後に「押せたか不安」が残りにくい

---

## フェーズ B

### テーマ

分析画面の初回表示を軽くする

### やること

1. 日別 / 商品別 / 時間帯別 / 曜日別の表示を skeleton 前提に整理
2. 重い分析グラフは lazy load 前提に寄せる
3. `no-store` 必須でない分析 API は短い `revalidate` を検討する
4. 画面ごとに「最初に必要な指標」と「後でよい集計」を分離する

### 完了条件

- 分析画面で真っ白待ちが減る
- 表が先に出て、グラフは後から入る
- 体感の読み込み時間が短く感じられる

---

## フェーズ C

### テーマ

設定系画面の無駄取得を減らす

### やること

1. `vendor/mobile-order`
2. `vendor/mobile-order/products`
3. `vendor/mobile-order/options`
4. `vendor/mobile-order/schedules`
5. `products/master`

などの設定画面で、

- 初回 server fetch
- client fetch
- mutate 後の全件再取得

のどこが不要か整理する。

### 完了条件

- 保存後の全画面ガクッと再読み込みが減る
- 設定画面の再表示が軽くなる

---

## 優先順位

### Must

1. 認証待ちのさらなる削減
2. 注文ダッシュボード / 公開注文 / POS の監視処理共通化
3. 分析画面の skeleton 統一

### ぜひやりたい

1. 設定画面の `no-store` 見直し
2. 分析 API の revalidate 導入
3. ローディング UI の全画面統一

### Better

1. 注文ダッシュボードの差分更新化
2. 分析の source 別内訳 lazy fetch
3. 画面単位の体感速度計測ログ

---

## 最初の着手順

1. 注文系のポーリング共通 hook を作る
2. `AuthProvider` の refresh 条件をさらに整理する
3. 注文ダッシュボードと公開注文/POSでその hook を使う
4. 次に分析画面の skeleton を整える

---

## メモ

今回の最重要テーマは、

**「毎回最新でなくてもよいものまで、毎回フルで取りに行っている状態を減らす」**

こと。

その上で、

**「待つ時は待っていると分かる」**

を全画面でそろえる。
