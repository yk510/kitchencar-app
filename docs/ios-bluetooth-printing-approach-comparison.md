# iPad Bluetooth 印刷方式 比較

最終更新: 2026-05-19

## 前提

- クリダス本体は **Next.js の Web アプリ**
- 将来的に iPad で Bluetooth レシート印刷を実現したい
- 実機が届く前に、実装を進められる土台を先に作っておきたい

## 比較対象

### 1. iPad 向けネイティブ補助アプリ

構成:
- クリダス本体は Safari / Web アプリのまま
- 印刷時だけ、補助アプリへ印刷 payload を渡す
- 補助アプリが Bluetooth プリンターと通信する

良い点:
- 既存 Web 画面への影響が小さい
- 印刷まわりだけ独立して開発できる
- POS 以外の画面をアプリ化しなくてよい
- まずは印刷機能だけを小さく PoC しやすい

弱い点:
- Web と補助アプリの 2 つを運用する必要がある
- 端末上でアプリ切り替え / ディープリンク復帰設計が必要
- Safari 側の状態維持を丁寧に考える必要がある

向いているケース:
- まずは **印刷機能だけ** 早く Bluetooth 対応したい
- 既存 Web アプリを大きく変えたくない
- MVP 検証を急ぎたい

### 2. iPad 向け WebView ラッパーアプリ

構成:
- クリダスを iPad アプリの WebView で開く
- 印刷や Bluetooth はアプリ側が担当する
- Web 側は `window.webkit.messageHandlers` などの bridge でネイティブを呼ぶ

良い点:
- 画面遷移中もアプリ内で完結しやすい
- 印刷だけでなく、将来
  - kiosk 制御
  - 端末固定運用
  - 音声通知
  - 端末設定
  まで広げやすい
- Safari 制約を避けやすい

弱い点:
- 補助アプリ案より初期コストが高い
- WebView 容器、認証、セッション維持の設計が必要
- 最初から少し大きめの実装になる

向いているケース:
- 将来的に iPad アプリを正式運用したい
- POS 画面や注文管理画面もアプリ寄りに育てたい
- 印刷以外のネイティブ機能も使いたい

## いまのおすすめ

### 短期

- **ネイティブ補助アプリ案を先に検証**

理由:
- 実機到着前に、Web 側の印刷 bridge 契約を先に固めやすい
- 既存 Web アプリ資産をほぼ維持できる
- Bluetooth 印刷だけにスコープを絞れる

### 中期

- もし iPad を POS 本番端末として広く使うなら、**WebView ラッパー案** に寄せる

理由:
- 印刷以外の運用改善も取り込みやすい
- Safari に依存しない設計へ寄せやすい

## 実装の考え方

どちらの方式でも、まず Web 側では次を共通化しておく。

1. `ReceiptPrintPayload`
2. 共通印字ドキュメント
3. ESC/POS などへの renderer
4. **Web → ネイティブ印刷 bridge**

つまり、最初に作るべきなのは **iPad ネイティブの完成形ではなく、Web 側の bridge 契約**。

## 今の結論

- **実機到着前に着手するなら**
  - `ネイティブ補助アプリ案` を第一候補
  - ただし bridge は `WebView ラッパー案` でも再利用できる形で作る

- そのため、Web 側は
  - `messageHandlers`
  - `custom URL scheme`
  の両方に乗せ替えやすい bridge を持つ

## 次にやること

2. 印刷 payload を bridge 経由で送る envelope を定義
3. 補助アプリ方式と WebView ラッパー方式の両方で使えるデータ契約にする
