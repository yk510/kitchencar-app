# Android + Bluetooth プリンター MVP 検証 実装計画

最終更新: 2026-05-19

## Phase 1: 検証対象を固定する

目的:
- 不確定要素を減らして、まず 1 つの構成で通るかを見る

やること:
- Android タブレット機種を 1 つ決める
- Bluetooth プリンター機種を 1 つ決める
- 印字幅を 58mm / 80mm どちらでいくか決める

完了条件:
- 検証環境が固定される

### Ticket 1 の固定結果

- タブレット: `Redmi Pad SE（Wi-Fi）`
- プリンター: `SII MP-B20`
- ブラウザ: `Android Chrome`
- 用紙幅: `58mm`

この組み合わせで、まず **注文番号控えの MVP 印字** を成立させる。

## Phase 2: 接続方式を判断する

目的:
- Web Bluetooth だけでいけるか、補助アプリが必要か見極める

やること:
- 対象プリンターで Web Bluetooth の PoC を行う
- 接続 / 送信 / 再接続 / スリープ復帰を確認
- 難しければ補助アプリ方式へ切り替える

完了条件:
- 技術方式を 1 つに決める

### Ticket 2 の進め方

- まずは **Android Chrome + Web Bluetooth** を先に試す
- 対象は `SII MP-B20`
- ここで確認するのは
  - デバイス選択できるか
  - GATT 接続まで進めるか
  - スリープ復帰後も再確認しやすいか
- GATT 接続が不安定、または不可なら **補助アプリ方式へ切り替える**

## Phase 3: 印刷 payload の再利用戦略を決める

目的:
- 既存の LAN 印刷実装資産を最大限使う

やること:
- 既存 `ReceiptPrintPayload` を Bluetooth 側でも共通利用する
- header / body / footer の整形は既存 formatter を流用する
- Bluetooth 側は送信層だけ差し替える

完了条件:
- payload 層は共通、送信層だけ分岐、という構造にする

## Phase 4: Bluetooth 送信層を追加

目的:
- Android 構成で印刷送信できるようにする

やること:
- 方針Aなら Web Bluetooth helper
- 方針Bなら補助アプリ連携 helper
- 接続失敗 / 再試行 / タイムアウトの設計

完了条件:
- テスト印刷ができる

## Phase 5: 注文管理 / POS の印刷導線に接続

目的:
- 現場運用で意味のある導線にする

やること:
- `料金受領を記録` 後の自動印刷
- `再印刷`
- 印刷失敗時の UI
- fallback 文言

完了条件:
- 現場で 1 サイクル回せる

## Phase 6: 運用評価

目的:
- 実機で現場投入できるか判断する

やること:
- 印刷速度
- 接続安定性
- 再接続
- 端末スリープ復帰
- 店員オペレーション負荷
を確認

完了条件:
- 継続採用 / LAN 継続 / 補助アプリ本実装 の判断ができる

## 技術判断の目安

### Web Bluetooth で進む条件

- 接続が安定する
- スリープ復帰後も再接続しやすい
- ブラウザ再起動時の再ペアリング負荷が許容範囲
- 印字速度が十分

### 補助アプリへ進む条件

- Web Bluetooth が不安定
- 再接続や復帰で店員負荷が高い
- 機種依存が強すぎる
- 印字制御が足りない

## 既存資産の再利用ポイント

- `ReceiptPrintPayload`
- 注文番号 / 注文内容 / 店舗名 / 注文日時の formatter
- 注文管理画面の自動印刷 / 再印刷 UI
- 失敗時 fallback の文言整理

## MVP の出口

1. Android + Bluetooth だけで十分運用できる
2. 補助アプリを足せば実用化できる
3. まだ LAN の方が現実的

のどれかを判断できる状態にする
